# 04. 收據 OCR

從紙本收據圖片建立傳票候選。

**Language**: [日本語](04-receipt-ocr.md) | [English](04-receipt-ocr_en.md) | **繁體中文**

> **讀完這章你能做到**
> - 從照片或 PDF 圖片抽出日期・店名・合計・適格請求書登錄番号、然後轉成傳票
> - 看懂可用的 OCR 引擎的差異與選擇
> - 看懂雲端送出前確認對話框的意義與「下次起不問」要不要勾
>
> **前提**：[01. 初次設定 § 7](01-setup_zh-TW.md#7-要用-ocrllm-才做的設定) 設好 OCR/LLM 引擎。

## 2. 取込步驟

導覽列「**收據**」進入 `Receipt` 畫面。

### 2-1. 選圖片

點「**1. 選擇圖像（亦可用相機拍攝）**」的檔案輸入：

- PC：檔案對話框選 JPG / PNG / WebP / HEIC
- 手機、平板：可從相片圖庫／現場拍攝／選檔案

選好後下方會顯示預覽。

> **拍攝小技巧**：
> - 平面、避免陰影
> - 整張收據在框內
> - 避開螢光燈反光
> - 1〜2 MP 解析度就夠。再高反而對 LLM rate limit 不利

### 2-2. 解析

按「**解析**」送到選中的引擎開始解析。

#### 雲端引擎（Gemini / 遠端 OpenAI 相容）：送出前確認對話框

因為會離開本機，按下去馬上跳 **CloudSendConfirmDialog**：

> 要送出圖片到 〇〇 嗎？
>
> ☐ 下次起不問

- 確認後按「**送出**」執行
- 「**取消**」中止
- 勾「下次起不問」後送出，之後**所有引擎**（OCR・CSV・訂單取込的 LLM 送出共通）都不再跳對話框

<!-- only:browser -->

### 2-3. 抽取結果確認・修正

解析完成後「**2. 抽取結果（可編輯）**」會展開：

| 欄位 | 內容 |
|---|---|
| 交易日 | 收據日期、`YYYY-MM-DD` |
| 店名 / 交易對象 | 店名（可編輯）|
| 合計金額（円）| 含稅合計（可編輯，整數）|
| 發票登錄號碼 | 認得到 T+13 位時才顯示（參考用）|
| 內訳 | 有品項時可展開（參考用、不會反映到傳票）|

<!-- only:browser -->
> **vision LLM 路 vs Tesseract 路的差別**：
> - vision LLM 店名・合計都能高精度抽出。連品項內訳也撈
> - Tesseract **只抽日期・合計・T+13 登錄號碼** 這 3 種以確定性規則拿。**店名與品項不推測、保留空白**。OCR 全文內部留著但不自動寫進傳票摘要
<!-- /only -->
<!-- only:native -->
> **vision LLM 路 vs Tesseract、作業系統內建的文字辨識 路的差別**：
> - vision LLM 店名・合計都能高精度抽出。連品項內訳也撈
> - Tesseract **只抽日期・合計・T+13 登錄號碼** 這 3 種以確定性規則拿。**店名與品項不推測、保留空白**
> - 作業系統內建的文字辨識除了上面 3 種，還會抽 **店名** 與 **品項**。它會回傳每個字詞的位置與大小，所以能把抬頭中字最大的那一行當成店名，並把抬頭與合計之間「左邊品名、右邊金額」的列當成品項
> - 兩者的 OCR 全文都留在內部，但不會自動寫進傳票摘要
<!-- /only -->

> 這是作業系統內建文字辨識的結果。請務必確認並修正合計金額、日期與店名。OCR 全文不會存進備註（只顯示在畫面上）。

### 2-4. 選對方科目・支付來源

抽取結果下方有 2 個下拉：

| 下拉 | 預設 | 意思 |
|---|---|---|
| **對方科目（經費）**| `5910 雑費` | 這張收據要計上的經費科目 |
| **支付來源** | `1110 現金` | 用什麼付的（現金・普通預金・未払金 等）|

如果是事業用、無家事分攤的單純經費，改成對應科目（例：餐飲 → `5170 接待交際費`、文具 → `5200 消耗品費`）。

刷卡的話**支付來源**改成 `2120 未払金`（有用輔助科目分卡的話、選該卡）。

### 2-5. 建立傳票

按「**建立傳票**」確定。借方＝經費／貸方＝支付來源 的 2 行傳票建立、首頁最近一覽會出現。

> 抽取結果有**發票登錄號碼**的話，該傳票行的 `invoiceCompliant` flag 會存成 `true`（消費税本則課税時可作為仕入税額控除對象）。

## 3. 各引擎實用 tips

### Gemini Vision

- 免費額度月幾百張不成問題、收據圖片 token 消耗少
- 拍歪一點、有部分陰影也撐得住
- 1〜2 MP 解析度就夠、再高反而拖速度・成本

### OpenAI 相容（Ollama / LM Studio 等）

- **必須選 vision 模型**（純文字模型遇到圖片輸入會掛）
- 推薦：`gemma4`、`ministral-3`、`llama3.2-vision` 等
<!-- only:browser -->
- Ollama 那邊：`OLLAMA_ORIGINS` 一定要把 aoiko 的 URL（例 `http://localhost:31527`）加進來
- aoiko 自己也要本機起（`npm run preview`）。HTTPS 配信版連不到 localhost
<!-- /only -->
<!-- only:native -->
- 指向 localhost 也不用額外設定，通訊由 App 代為轉發
<!-- /only -->

### Tesseract

- **vision LLM 不能用／不想用**時的選項
- 預設店名・品項抽不到、心理上接受
- T+13 登錄號碼相當穩（regex 抽出）
- 日期・合計撈得到算運氣好。務必人工確認・修正
- 語言資料已內附，第一次取得後就能完全離線運作。只有想換別的版本（例如精度較高的 best）時才需要在設定中指定來源
<!-- only:native -->

### 作業系統內建的文字辨識

- 不用 LLM、也不用另外下載
- 除了日期・合計・登錄號碼，還會抽 **店名** 與 **品項**。每個字詞都帶位置與大小，所以取抬頭中字最大的那一行當店名，抬頭與合計之間「左品名、右金額」的列當品項。辨識錯了會照樣出現，仍需確認
- 合計取「合計」那一列最右邊的金額。就算同列還印著件數（`合計／ 1点 ¥159`）也不會誤取件數
- 電話號碼、收銀機號碼、單據號碼同樣是「左邊文字、右邊數字」。字詞裡含分隔符號的、以及左邊是日期或純數字的列，都不當成品項。寧可不撈也不要撈錯
- 手邊的樣本日期與合計都讀得出來，但試過的張數不多。合計與日期務必人工確認
- 登錄號碼開頭的 `T` 有時會掉。文字辨識每個字詞會回傳多個候選，所以會依序尋找符合 `T` 加上剛好 13 位數字的候選——實測有過第 3 個候選才是正確的例子。所有候選位數都不對就留空（格式正確的錯號碼，看也看不出來）
- **不是每台裝置都能用**。作業系統那邊要裝有日文的文字辨識才會動。在設定中選下去的當下就會檢測，不能用時設定畫面會出現說明。選項本身不會消失，所以之後在作業系統加上日文再回來選一次即可
<!-- /only -->

## 4. 抽取不出來時的對策

| 症狀 | 對策 |
|---|---|
| 合計金額對不上 | 重拍 or 手動修正。LLM 路通常很少，本機辨識路常發生、本來就要人工 |
| 日期空 | 「YYYY/MM/DD」「令和○年」兩種格式都試過了。直接手動輸入也行 |
| 店名亂碼 | 提升拍攝品質與解析度。Tesseract 不抽店名，只能手動補 |
| 發票號碼沒認出來 | 號碼印字部分要亮、重拍。LLM 系 1〜2 mm 小字也能抓 |
| 連線錯誤 | 設定 →「連線測試」確認 API 金鑰・endpoint |

## 5. 隱私注意

- 收據有第三方個資（顧客名・住址）時，送雲端引擎前要再確認
- 高機密的收據（個人醫療費・特殊事業的取引先 等）用本機辨識路或 Ollama on localhost 比較安心
